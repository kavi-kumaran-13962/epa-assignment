# Error analysis

This is a structured walk through the residual errors made by the trained
LR + TF-IDF + handcrafted-features model on the held-out EPA test split
(3,900 candidate rows, 1,870 positive, 2,030 negative). Every example
below comes from the actual Enron dataset and the actual trained model;
the breakdown was generated by the snippet at the end of this document
so it is reproducible from `models/epa_model.joblib`.

## Headline numbers

Held-out test set, threshold 0.5:

| metric | value |
|---|---|
| precision | 0.823 |
| recall | 0.872 |
| F1 | 0.847 |
| ROC-AUC | 0.931 |
| PR-AUC  | 0.923 |
| support | 3,900 (1,870+ / 2,030−) |

Confusion: TP = 1,630, FP = 351, FN = 240, TN = 1,679.

## Where the errors live

| bucket | count | fraction of bucket | comment |
|---|---|---|---|
| Total FPs | 351 | 17 % of negatives | over-assigning to a recipient |
| Total FNs | 240 | 13 % of positives | missing a responsible person |
| FPs in multi-recipient HITs | 322 | **92 %** of FPs | dominant FP pattern |
| FPs in single-recipient HITs | 29 | 8 % of FPs | tiny – single-recipient F1 = 0.96 |
| FNs where candidate is sender | 42 | 17 % of FNs | senders committing themselves |
| FNs where candidate is Cc | 199 | 83 % of FNs | multi-recipient miss; "and X" elision |
| FPs where task contains "you/your" | 144 | 41 % of FPs | implicit-pronoun overreach |

The two takeaways:

1. **Multi-recipient cases dominate the error budget.** The single-recipient
   slice is essentially solved (F1 = 0.96); the lift from any future work
   on this dataset is concentrated in HITs with ≥2 recipients.
2. **Senders are a directional bias.** The model has learned the strong
   prior that the sender is rarely the responsible party (P = 0.044 in
   our training set), and pays for it on the minority of HITs where the
   sender does commit themselves.

## How errors are categorized

`src/models/metrics.py` slices the test set by scenario (single- vs
multi-recipient, task contains "you/your", explicit candidate name in
task, no-one cases, candidate-is-sender, perfect-agreement-only). Per
slice the `evaluation.md` report includes precision / recall / F1.

To inspect specific examples directly:

```python
import joblib
from src.models.split import group_train_test_split
from src.models.train import _read_examples
from src.utils.io import load_config

cfg = load_config("config.yaml")
df = _read_examples(cfg["paths"]["examples_csv"])
_, _, test = group_train_test_split(
    df,
    group_key=cfg["split"]["group_key"],
    test_size=cfg["split"]["test_size"],
    val_size=cfg["split"]["val_size"],
    random_state=cfg["split"]["random_state"],
)
bundle = joblib.load(cfg["paths"]["model_path"])
test["score"] = bundle["pipeline"].predict_proba(test)[:, 1]
test["pred"]  = (test["score"] >= bundle["default_threshold"]).astype(int)

fp = test[(test.pred == 1) & (test.label == 0)].sort_values("score", ascending=False)
fn = test[(test.pred == 0) & (test.label == 1)].sort_values("score")
```

Pattern: strong imperative + `is_to` + nothing in the task that

Pattern: the sender is sometimes annotated as responsible (typically when
the email is a reply that re-stretches a prior commitment, or when "me"
in the task refers to the sender themselves). Our `is_sender=1` feature
weighs strongly against assignment, so these all sit at the floor of the
score distribution.

## Error categories and concrete next steps

| # | Error type | Example pattern | Likely cause | Possible improvement |
|---|---|---|---|---|
| 1 | Multi-recipient over-assignment | "provide me your comments." with 3 To-recipients; we mark all of them | Pragmatics features (`please`, imperative) + `is_to` dominate; nothing tells the model only one of them is meant | Listwise / pairwise scoring with a softmax across candidates per HIT; or a "responsible-count" head trained jointly. |
| 2 | Implicit "you" (singular) | "Please send me the deck by Friday" with one recipient | Task lacks explicit name; today the model already nails this slice (F1 = 0.96 single-recipient) but residual cases are typically forwarded threads | Parse the immediately preceding turn from quoted history; add features over it. |
| 3 | Implicit "you" (plural) | "Please complete a draft by Friday." with multiple To recipients | Same as (1) but the right answer is *all* recipients; many FPs/FNs flip-flop here | Add a `n_responsible_predicted` head; calibrate per-HIT total. |
| 4 | Conjunction "X and you" | "Can you and Brad review this?" | First-name match for Brad fires; the "you" still needs to be resolved to the To list | Conjunction-aware addressee tagging; use spaCy / a tiny dependency parse over the task. |
| 5 | Sender commits themselves | Replies of the form "I'll handle this" or "I will respond" | `is_sender=1` is strongly negative; current pragmatics features don't catch first-person commitments | Add features for first-person futures ("I'll", "I will", "let me") combined with `is_sender`. |
| 6 | Sender responsible via "me" | "Please send the file to me" — sender wants the file | `me/myself` in task is not currently a feature; sender's prior pulls scores down | Feature: `task_contains_first_person_obj` × `is_sender`. |
| 7 | Task references a 3rd party | "Please ask Jeff to contact trader." (Jeff is not on To/Cc) | Pragmatic cues fire; the model assigns a To recipient because that's the only candidate available | NER over the task; if a name in the task is *not* in the candidate list, lower scores for everyone. |
| 8 | Group / alias recipient | `webmaster@stadtbau-amberg.de`, `sales@enron.com` | Alias has no useful name; structural features dominate | Detect aliases (no first/last name + role-y local part) and either skip them or expand via a directory. |
| 9 | Sentence segmentation noise | Body has runs of `<br/>` that fuse two sentences | Same-sentence-as-task / proximity features misfire on the longest fused fragments | Better sentence segmenter on body before feature extraction. |
| 10 | Polite but uncommitted | "If you have time, would you take a look?" | Pragmatics features fire (`would you`, `?`), but annotators disagreed on whether this is a real assignment (these HITs sit in the dropped-for-consensus or noisy band) | Calibrated thresholds + product-side review-queue for low-confidence positives. |

## What we'd prioritize next

If we had another half-day on this dataset, in priority order:

1. **Listwise scoring with a "no-one" slot.** The single biggest leverage
   point is the multi-recipient over-assignment problem (92 % of FPs).
   Replacing the per-candidate independent classifier with a softmax over
   candidates plus a no-one option would naturally bound how many people
   per HIT can be responsible.
2. **First-person commitment features for the sender.** Adding
   `task_first_person_subject_with_future` (`I will`, `I'll`, `let me`)
   and crossing it with `is_sender` should recover most of the 42
   sender-FN cases without hurting the broader precision.
3. **Out-of-candidate-list NER.** A simple capitalised-token detector
   over the task that flags "is this a person not on To/Cc?" would
   directly address category 7 and the no-one cases.

Those three together would, in our experience with similar
addressee-tagging problems, account for the majority of the residual
errors after a strong logistic-regression baseline.
